# 1.9.0 macOS 与 ADB 启动验收

日期：2026-10-27。当前开发与验收机器为 Windows x64；没有 Mac 执行环境。

## macOS 交付实现

- 从 Google 官方 `platform-tools-latest-darwin.zip` 获取 Platform-Tools 37.0.1，原归档 SHA-256 为 `ee39ad5967e95c2a07f04dbcbde96b1a0c916ba376096db5d2f498b7727a5d1d`。
- `vendor/adb/macos` 保存原始 adb、lib64/libc++.dylib、NOTICE.txt 与 source.properties；清单记录每个必需文件 SHA-256，构建和首次发现 ADB 时核对。
- ADB 与 dylib 的 Universal Mach-O 结构均经检查，包含 CPU_TYPE_X86_64 与 CPU_TYPE_ARM64。macOS Intel 和 Apple Silicon 自动选择这份二进制，Windows 仍选择 Windows 版本。
- scrcpy Android 服务端与现有浏览器解码、录制实现复用；没有增加 Homebrew、Java、FFmpeg 或 scrcpy.exe 依赖。
- 对 Windows 打包可能丢失的 POSIX 执行权限，在完整性校验通过后恢复。文件系统不允许修复则明确报错，不使用 sudo，不修改 Gatekeeper 或隔离属性。
- 同一个 tgz 包含 Windows/macOS 运行资源。当前是 Harness 插件，不是签名、公证后的独立 Mac 应用安装器。

## 本机 ADB 报错调查与修复

用户报告 `D:\android\sdk\platform-tools\adb.exe -P 5037 start-server` 返回 `could not read ok from ADB Server`。

本机 `%TEMP%/adb.log` 记录：2026-10-26 22:17:10，两个旧版 ADB 34.0.0 进程同时启动。PID 2892 成功监听，PID 20200 随后报 `cannot bind to 127.0.0.1:5037`、Windows 错误 10048。因此至少该次失败由并发争用端口造成，不是手机未授权。调查时 PID 2892 服务仍正常，旧 ADB 的同一 start-server 命令返回 0，已授权手机可列出；没有停止或重启共享服务。

插件现在在启动前用 ADB 协议检查服务；正常响应时直接复用。同进程同端口的并发请求合并为一次启动，跨进程竞争失败后短暂复核服务器状态，仅有有效 ADB 响应才作为恢复成功。真实失败仍抛出，并显示 `ADB_SERVER_START_FAILED` 诊断。不重试手机操作，不自动 kill-server。

## 必须在 Mac 上补做

分别在 Intel Mac 与 Apple Silicon Mac 上，安装兼容的 Harness 与同一个 `dsh-android-1.9.0.tgz`，确认诊断显示 `adb.source=bundled`。使用真实用户安装方式验证首次启动的安全提示和权限行为。开发环境可执行：

```sh
npm ci
npm run typecheck
npm run build
npm test
mkdir -p .build
npm pack --pack-destination .build
node scripts/runtime-package-smoke.mjs --device
```

该脚本在 Mac 上主动清除测试副本的执行位，再检查运行时是否恢复；还检查缺少 dylib、损坏 adb 时拒绝运行。连接已授权的 Android 手机后验证应用列表和投屏数据。随后需用 Harness UI 核对实际视频解码、输入、文件上传下载哈希、录制、拔插重连，以及干净用户配置下的首次启动。

这些 Mac 检查目前**未执行**，不能用 Windows 测试或 Mach-O 结构检查替代。具体最低 macOS 版本以宿主 Harness、WebCodecs 和真实二进制运行验证共同确定，尚未承诺最低系统版本。

macOS 安全提示依据：[Apple 官方说明](https://support.apple.com/en-us/102445)。ADB 来源：[Google 官方 Platform-Tools](https://developer.android.com/tools/releases/platform-tools)。
